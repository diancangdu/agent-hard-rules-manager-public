# 分层判断表

这份文档回答一个问题：**一条规则该只进 notebook，还是该同时上 hook？**

---

## 一、一句话判据

> **漏掉这条规则的后果，是「出事」，还是「不够好」？**
>
> **出事的才上 hook；不够好的只进 notebook。**

两层不是「强弱」关系，而是**失效方式**不同：

| 层 | 强制力来源 | 失效时的表现 |
| --- | --- | --- |
| `notebook` | agent 主动查询 + 自觉遵守 | **静默**（漏了没人知道） |
| `hook` | 代码在工具调用前拦截（`exit 2`） | **显式**（模型看到 blocked 理由） |

hook 是窄而硬的一层：它只看得见**单次工具调用的入参**，所以它只能承担那些「能被正则稳定识别」的红线。把判据落到可操作的三条：

1. 漏了会不会造成**不可逆损失**（数据、凭据、系统盘）？
2. 这个损失能不能在**单次工具调用的入参文本**里被稳定识别？
3. 识别用的模式会不会**大面积误伤**正常操作？

三条都「是」，才上 hook。有一条「否」，留在 notebook。

## 二、现有 22 条规则的归属

当前状态：**19 条只进 notebook，3 条上 hook**（`RULE_001` / `RULE_003` / `RULE_005`）。

| ID | 标题 | 分类 | layer | 判断理由 |
| --- | --- | --- | --- | --- |
| RULE_001 | 敏感信息保护 | 安全 | **notebook + hook** | 漏了 = 密钥/凭据进源码 = 出错即不可逆泄露（出事）；且 `write`/`edit` 的 `content` 里 `sk-…`、`AKIA…`、`-----BEGIN … PRIVATE KEY-----` 等模式可稳定识别；模式足够特异，误报率低。 |
| RULE_002 | 重构代码规范 | 行为 | notebook | 漏了最多是改得不理想，属「不够好」。「是否先理解了原代码、是否保持既有行为」无法从单次调用入参判定。 |
| RULE_003 | 禁止危险命令 | 安全 | **notebook + hook** | 漏了 = 不可逆数据丢失（出事）；`rm -rf /`、`DROP TABLE`、`Remove-Item -Recurse -Force`、`mkfs`/`diskpart` 等可在命令文本里稳定匹配。 |
| RULE_004 | 修改配置文件必须保留备份 | 技术 | notebook | 「是否已先备份」是**状态**判断，入参里看不到；且多数配置可从源码/默认值重建，达不到「出事」级。 |

| RULE_006 | 三模型协同总指挥规则 | 协作 | notebook | 协作分工约定，没有可机器判定的单次调用特征。 |
| RULE_007 | 协同前先商量最优方案 | 协作 | notebook | 「是否已商量」是跨轮次过程，无法从入参判定。 |
| RULE_008 | 三模型互助规则 | 协作 | notebook | 同 RULE_007，属协作行为约定。 |
| RULE_009 | 用户说调动/解除词时，一键调度三兄弟并自动解除 | 三模型协同 | notebook | 触发源是**用户说的话**，而 hook 只看工具入参，结构上看不到。 |
| RULE_010 | 通用项目调度：任何时刻任何项目可调动/解除三兄弟 | 三模型协同 | notebook | 调度意图需结合项目上下文判断，非工具入参可表达。 |
| RULE_011 | 三兄弟调动默认 15 分钟无活动自动解除 | 三模型协同 | notebook | 「15 分钟无活动」是时间 + 跨轮次状态，不是入参。 |
| RULE_012 | 总指挥完成前必须等兄弟完成 | 行为 | notebook | 「兄弟是否都已完成」是外部跨轮次状态。 |
| RULE_013 | 开工即自动连接兄弟通信服务器 | 行为 | notebook | 「是否已连接」是运行状态；且启动本地服务的命令本身并不危险，不值得设闸。 |
| RULE_014 | 默认隐藏控制台黑窗 | 行为 | notebook | 启动方式太多样（`pythonw`、`subprocess`、计划任务、`Start-Process`…），没有稳定的单一入参模式；强行设闸会大面积误伤。 |
| RULE_015 | 重复性操作自动沉淀为 Skill | 行为 | notebook | 「是否重复出现」需要历史判断。 |
| RULE_016 | 部署与发布前必须确认环境与回滚方案 | 技术 | notebook | 「是否已确认」是状态判断；「部署」的命令形态过于多样，无法用一条模式覆盖。 |
| RULE_017 | 工具类文件优先存放 F 盘 | 行为 | notebook | 倾向性规则，且自带两个例外（F 盘可用空间 < 40GB、用户特别指定），机器无法判断；「工具类文件」也无法从路径正则识别。**对比 RULE_005**：那条是绝对红线，才上 hook。 |
| RULE_018 | 安装前先检查本地是否已有 | 行为 | notebook | 需要查询本地现状（装了没有），正则做不到。 |
| RULE_019 | Projectless 任务目录必须固定且防更新漂移 | 技术 | notebook | 目录稳定性是跨时间状态。 |
| RULE_020 | 复杂任务主动启用多子 agent 协作模式 | 协作 | notebook | 「复杂」是主观判断。 |
| RULE_021 | 任务前加载经验、任务后反思沉淀 | 协作 | notebook | 「是否已加载 / 已反思」是流程状态。 |
| RULE_022 | 有用的经验由主 agent 自行判断并写入经验库 | 协作 | notebook | 「有用」是主观判断。 |

**可归纳的规律**：上了 hook 的 3 条，全部满足「不可逆损失 + 单条命令/单次写文件里就能看出来 + 模式特异」。19 条 notebook 规则的失败原因，可以归成四类——需要跨轮次状态、需要查本地现状、触发源是用户的话、判据本身是主观的。

## 三、后续新增规则该怎么判

按顺序问下去，第一个「否」就是归属。

```
新规则
  │
  ├─ 1. 漏掉它的后果是「出事」吗？（不可逆损失 / 凭据泄露 / 系统盘污染）
  │     否 ──► notebook（结束）
  │     是
  │
  ├─ 2. 这个「出事」能在单次工具调用的入参文本里看出来吗？
  │       （只需要 tool_name + tool_input，不依赖历史、文件系统、用户说过的话）
  │     否 ──► notebook（结束）
  │     是
  │
  ├─ 3. 能写出稳定的 tools / fields / any_of 吗？（模式具体，不是「任何写文件」「任何命令」这么宽）
  │     否 ──► notebook（结束）
  │     是
  │
  ├─ 4. 这个模式会误伤大量正常操作吗？（拿不准就先用真实命令试跑守卫自检用例）
  │     会 ──► notebook（结束）
  │     不会
  │
  └─ notebook + hook
```

**默认从 notebook 开始，是更稳的选择。** 加 hook 的成本不只是写几行正则：一次误报就会拦下用户的正常操作，而 agent 当时看不到「为什么」，体验上等同于工具坏了。所以判不准时，先只进 notebook，观察一段时间；确认真的漏过，再提升为 hook。

### 提升一条规则到 hook 的操作（目前需手工）

`layer` 与 `hook` **无法**通过 `add_rule.py` 或 MCP `add_rule` 写入——那样加出来的规则没有 `layer` 字段，闸门会忽略它（即事实上只进 notebook）。上 hook 需要有意地手工编辑 `rules/rules.json`：

```json
{
  "rule_id": "RULE_023",
  "title": "规则标题",
  "layer": ["notebook", "hook"],
  "hook": {
    "tools": ["bash", "pwsh"],
    "fields": ["command"],
    "any_of": ["(?i)\\b你的正则1\\b", "(?i)\\b你的正则2\\b"],
    "all_of": [],
    "action": "deny",
    "reason": "命中死规则 RULE_023（规则标题）：说明为什么被拦、以及应该改用什么做法。"
  }
}
```

要点：

- **`reason` 是给模型看的唯一线索**（走 stderr 回传）。必须写清「为什么拦 + 该怎么做」，只写「违反了规则」等于没写。
- `any_of` 与 `all_of` 至少写一个，否则该 hook 会被跳过。
- `tools` 为空时会匹配所有工具——几乎总是写得不具体，请显式列举。
- 改完跑一次自检确认没有把自己正常的操作也拦了：

```bash
python hooks/scripts/pretooluse_guard.py --selftest
```

自检里的用例就是现成的回归基线（当前 11/11 通过），新增 hook 后建议照着格式补一条正例一条反例。

## 四、两个必须说清的边界

1. **hook 只做 deny，不做 allow。** `pretooluse_guard.py` 会跳过任何 `action` 不是 `deny` 的规则。所以这一层只能用来「拦住危险动作」，不能用来「预先放行/减少确认」。想要更少确认提示，得改宿主 agent 的权限配置，不是这里。
2. **hook 不能替代 notebook。** 上 hook 的规则 `layer` 是 `["notebook","hook"]`——它仍然在规则本里。也就是说：闸门负责「拦住明确的那几种写法」，规则本负责「理解为什么要拦」。换一种刁钻写法就能绕过正则，此时只有 notebook 层（agent 自己读懂规则意图）还起作用。
